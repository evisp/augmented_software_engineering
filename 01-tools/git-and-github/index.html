    Git & GitHub¶

    75 min Tools Needs: Shell Basics, a GitHub account

    Git saves snapshots of your work. GitHub stores those snapshots online so you do not lose them and other people can see them. In this tutorial you set both up, push your first repository, then learn to branch, merge, resolve a conflict and undo a mistake.

    Why this matters¶

    You will write a lot of code in this program. Some of it will work and then stop working, and you will want yesterday's version back. Git gives you that.

    There is a second reason. When you apply for a job, your GitHub profile is one of the first things a hiring manager opens. Every project you finish here ends up there, and the Checker reads your work from it. Start building that history on day one.

    How Git works¶

    Four places hold your work. Three are on your laptop, one is on GitHub. Each command moves your work from one place to the next.

    Keep this picture in your head. Most Git confusion comes from not knowing which of the four boxes your work is sitting in right now.

    Step 1: Tell Git who you are¶

    Git writes your name on every commit. Set it once, in the Ubuntu terminal:

    git config --global user.name "Your Full Name"
git config --global user.email "your-email@example.com"
git config --global init.defaultBranch main

    Use the same email address as your GitHub account. If the two do not match, your commits show up on GitHub without your profile attached. The last line makes every new repository start on a branch called main, the same name GitHub uses.

    Nothing prints when this works. Check it:

    git config --global --list

    Step 2: Let your laptop talk to GitHub¶

    GitHub does not accept your account password in the terminal. You authenticate with a Personal Access Token instead: a long random string that works like a password, but only for what you allow and only until it expires.

    1. On GitHub, open Settings, then Developer settings, then Personal access tokens, then Fine-grained tokens.
    2. Click Generate new token. Give it a name and an expiry of 90 days.
    3. Under Repository access, choose All repositories. Under Permissions, set Contents to Read and write.
    4. Click Generate token and copy it. GitHub shows it once and never again, so store it in a password manager now.

    Then tell Git to remember it:

    git config --global credential.helper store

    The first time you push, Git asks for a username and a password. Type your GitHub username, then paste the token as the password. Git saves it and stops asking.

    The gh tool creates and stores a token for you through the browser.

    sudo apt update && sudo apt install -y gh
gh auth login

    Choose GitHub.com, HTTPS, yes to authenticate Git with your GitHub credentials, then login with a web browser. Copy the one-time code, press Enter and finish in the browser.

    Check it worked with gh auth status.

    Never put your token in a URL or a file you commit

    You will find advice online to clone with https://username:token@github.com/.... It works, and it leaks. Git writes that URL into .git/config, your shell saves it in its history, and one screenshot in Slack gives someone else access to your account. If a token ever leaks, delete it on GitHub straight away and make a new one.

    Step 3: Create a repository on GitHub¶

    A repository, or repo, is a project folder that Git tracks. It is easiest to create it on GitHub and copy it down.

    1. On GitHub, click the green New button.
    2. Name it git-practice.
    3. Leave it public, and leave Add a README file unchecked.
    4. Click Create repository.

    Step 4: Clone it to your laptop¶

    Cloning downloads the repo and connects your local folder to GitHub. That connection is called a remote, and Git names it origin.

    cd ~/holberton
git clone https://github.com/your-username/git-practice.git
cd git-practice
git remote -v

    You should see the clone warn that the repository is empty, and two origin lines pointing at GitHub. The warning is fine.

    Step 5: The everyday loop¶

    Make a change, check it, stage it, commit it, push it. You will run this loop hundreds of times.

    echo "# Git practice" > README.md
git status

    git status is the most useful command in Git. Run it whenever you are unsure where things stand. Right now it lists README.md as untracked: Git sees the file but is not saving it yet.

    git add README.md                 # stage it
git commit -m "Add README"        # save a snapshot locally
git push -u origin main           # send it to GitHub

    The -u links your local main to GitHub's main, so from now on git push and git pull are enough. Refresh the repo page in your browser. Your file is there.

    To see what you have saved so far:

    git log --oneline

    Write commit messages in the imperative

    Write "Add login form", not "Added login form". Git's own messages read that way, so your history stays consistent. If a message needs the word and, you are probably saving two changes at once. Make two commits.

    Step 6: Ignore what does not belong¶

    Some files should never be committed: caches, editor settings, dependencies you can reinstall, and above all secrets. List them in a file called .gitignore at the root of the repo.

    .gitignore
    # Python
__pycache__/
*.pyc
.venv/

# JavaScript
node_modules/

# Secrets and local settings
.env
.vscode/

    git add .gitignore
git commit -m "Add .gitignore"
git push

    Now create a file called .env and run git status. Git does not list it. Ignored files stay on your laptop and never reach GitHub.

    .gitignore does not untrack files already committed

    If you committed a file before ignoring it, Git keeps tracking it. Stop tracking it with git rm --cached filename, then commit. If it was a secret, treat it as leaked: it is still in the history.

    Step 7: Work on a branch¶

    A branch is a separate line of commits. You make one for each change, work there without touching main, and merge it back when it is ready.

    git switch -c feature/greeting      # create the branch and move to it
echo "Hello from a branch" > greeting.txt
git add greeting.txt
git commit -m "Add greeting"
git push -u origin feature/greeting

    git branch lists your branches and marks the current one with *. git switch main moves back. Notice that greeting.txt disappears from your folder on main: it only exists on the branch so far.

    Step 8: Merge, and resolve a conflict¶

    To bring the branch into main, switch to main and merge:

    git switch main
git merge feature/greeting
git push

    Most merges finish by themselves. A conflict happens when both branches changed the same lines, and Git cannot know which version you want. Make one on purpose so you know what it looks like:

    git switch -c feature/title
echo "# Git practice, branch version" > README.md
git commit -am "Change title on branch"

git switch main
echo "# Git practice, main version" > README.md
git commit -am "Change title on main"

git merge feature/title

    Git stops and reports a conflict in README.md. Open the file:

    <<<<<<< HEAD
# Git practice, main version
=======
# Git practice, branch version
>>>>>>> feature/title

    The part above ======= is what main has. The part below is what the branch has. Edit the file so it says what it should, delete all three marker lines, then finish the merge:

    git add README.md
git commit -m "Merge feature/title"
git push

    VS Code highlights conflicts and offers Accept Current, Accept Incoming and Accept Both buttons above each one. They do the same editing for you, but read the result before you commit.

    Step 9: Undo a mistake¶

    Git has two main ways to undo a commit. The difference is whether you rewrite history or add to it.

    git revert adds a new commit that does the opposite of an old one. Nothing disappears, so it is safe on any branch other people use, including main after you have pushed.

    git log --oneline          # find the commit's short hash, e.g. a1b2c3d
git revert a1b2c3d         # Git opens an editor for the message; save and close
git push

    git reset moves the branch back to an earlier commit, as if the later ones never happened. Use it only on commits you have not pushed, because it rewrites history that others may already have.

    Command Commit removed? Your changes
    git reset --soft HEAD~1 Yes Kept, and still staged
    git reset HEAD~1 Yes Kept in your files, unstaged
    git reset --hard HEAD~1 Yes Deleted. There is no undo button

    HEAD~1 means "one commit before the current one". The safe default when you are unsure is git revert.

    AI in the loop

    Paste the output of git status or a conflict into Copilot Chat and ask what state your repository is in and what your options are. Assistants are good at reading Git output. Ask for an explanation rather than a command, and never run reset --hard or a force push because an assistant suggested it until you know what it deletes.

    When something goes wrong¶

    fatal: not a git repository

    You are not inside the repo folder. Run pwd, then cd into the folder you cloned.

    Authentication failed when you push

    The token is wrong or expired, or you typed your GitHub password instead of the token. Make a new token, run rm ~/.git-credentials, and push again. Or run gh auth login.

    Updates were rejected because the remote contains work

    Someone pushed to GitHub after you last pulled. Run git pull, resolve any conflicts, then push again.

    Please tell me who you are

    You skipped Step 1. Set your name and email, then commit again.

    I committed to main instead of a branch

    If you have not pushed yet: git switch -c feature/name to keep the commit on a new branch, then git switch main and git reset --hard origin/main to put main back the way GitHub has it.

    Explain it to someone¶

    • How to configure Git with your name and email
    • How to create a repository on GitHub and clone it locally
    • What the working directory, staging area and history are, and which command moves work between them
    • What .gitignore is for, and what belongs in it
    • How to push and pull, and how a Personal Access Token is used
    • What a branch is, and how to create and switch between them
    • How to merge a branch, and how to resolve a conflict
    • The difference between git reset and git revert, and when to use each

    Quick reference¶

    Command What it does
    git status Show what changed and what is staged
    git add file / git add . Stage one file / everything
    git commit -m "message" Save a snapshot locally
    git push / git pull Send commits to GitHub / bring them down
    git log --oneline List commits, one per line
    git switch -c name Create a branch and move to it
    git switch name Move to an existing branch
    git merge name Merge a branch into the current one
    git revert hash Undo a commit with a new commit
    git reset HEAD~1 Remove the last local commit, keep the changes
    git rm --cached file Stop tracking a file without deleting it
