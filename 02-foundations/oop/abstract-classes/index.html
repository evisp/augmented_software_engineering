    Abstract Classes & Interfaces¶

    90 min Object-Oriented Design Needs: Inheritance & Polymorphism

    Inheritance lets classes share code. This tutorial is about sharing promises: what every class of a kind must be able to do. You turn Account into an abstract contract, let gift cards pay alongside accounts, give the wallet a transaction log that behaves like a list, and add reusable behaviour with mixins. By the end, the wallet's design is something you could hand to another developer and they would know exactly what each class guarantees.

    Why this matters¶

    Version 2 works, but it relies on good behaviour. Nothing stops someone creating a plain Account, which has no real end-of-month rule, or adding a new account type and forgetting month_end. The mistake shows up much later, as a wrong balance.

    Large codebases, frameworks and libraries all deal with this the same way: they define contracts that classes must fulfil, and check them as early as possible. Knowing how to read and write those contracts is what lets you plug your code into someone else's.

    Where we left off¶

    Start from version 2, or the tag v2-inheritance: an Account base class with SavingsAccount and CheckingAccount below it. The wallet now has three new requirements:

    1. There is no such thing as a plain account. Every account type must define its own end-of-month rule.
    2. Customers can also pay with gift cards. A gift card has a code and a value, but it is not an account.
    3. Accounts and gift cards keep a history of every transaction, and can be exported as JSON for other systems.

    This is where the design is heading:

    Dashed outlines mark contracts, italic names mark abstract parts, and the hollow arrowheads point from a class to what it inherits from or implements. You will meet this notation properly in the UML project.

    Step 1: Abstract classes and @abstractmethod¶

    An abstract class is a class that is not meant to be used on its own. It holds the code its subclasses share, and declares the methods each subclass must provide. Python's abc module provides the tools: inherit from ABC, and mark the required methods with @abstractmethod.

    from abc import ABC, abstractmethod


class Account(ABC):
    """Abstract base for wallet accounts holding money, in whole lek."""

    # __init__, owner, balance, deposit, withdraw, __str__, __repr__
    # stay exactly as in version 2

    @abstractmethod
    def month_end(self):
        """Apply end-of-month rules and return the new balance."""

    The body of month_end is now just a docstring. It says what the method must do, not how. Python then enforces the contract in two places.

    You cannot create the abstract class itself:

    Account("Ada", 500)
# TypeError: Can't instantiate abstract class Account without an
# implementation for abstract method 'month_end'

    You cannot create a subclass that forgets the method:

    class BusinessAccount(Account):
    pass


BusinessAccount("Acme", 10)
# TypeError: Can't instantiate abstract class BusinessAccount without an
# implementation for abstract method 'month_end'

    The error comes when the object is created, not when month_end is finally called at the end of the month. That is the whole point: the mistake surfaces at once, on the line that caused it.

    SavingsAccount and CheckingAccount already define month_end, so they satisfy the contract and work unchanged. Define it in BusinessAccount and that works too:

    class BusinessAccount(Account):
    def month_end(self):
        return self._balance


acme = BusinessAccount("Acme", 10)
acme.deposit(5)          # 15: deposit is inherited, as before

    Notice what an abstract class is not: it is not empty. Account still contains all of its working code, deposit, withdraw, the properties and the string methods. An abstract class is a partly built class: shared code, plus clearly marked gaps that every subclass must fill.

    In version 2, the plain Account.month_end did nothing. That was a hint. A method that "does nothing, override me" is a missing contract.

    Step 2: Interfaces¶

    An abstract class that contains only abstract methods, and no code at all, describes pure capability: what an object can do, and nothing about how. Other languages call that an interface and have a keyword for it. Python models it with the same tool, an ABC.

    Both accounts and gift cards can pay. That shared capability becomes an interface:

    class Payer(ABC):
    """Interface: anything that can pay an amount."""

    @abstractmethod
    def pay(self, amount):
        """Pay amount, or raise ValueError; return what is left."""

    Account now implements Payer. Paying from an account means withdrawing, so pay simply calls withdraw:

    class Account(Payer):
    ...

    def pay(self, amount):
        """Pay amount from this account; return the new balance."""
        return self.withdraw(amount)

    Because Payer inherits from ABC, Account is still abstract, with two methods in its contract: pay, which it implements, and month_end, which it leaves to its subclasses. Thanks to polymorphism, linus.pay(300) runs the checking version of withdraw, overdraft and all.

    A GiftCard is not an account, so it must not inherit from Account. But it can pay, so it implements the same interface:

    class GiftCard(Payer):
    """A prepaid card with a fixed value. It is not an account."""

    currency = "ALL"

    def __init__(self, code, value):
        """Create a gift card with a code and a starting value."""
        if not isinstance(code, str) or not code.strip():
            raise ValueError("code must be a non-empty string")
        _check_amount(value)
        self._code = code.strip()
        self._value = value

    @property
    def value(self):
        """What is left on the card."""
        return self._value

    def pay(self, amount):
        """Pay amount from the card; return the value left."""
        _check_amount(amount)
        if amount > self._value:
            raise ValueError("not enough value on the card")
        self._value -= amount
        return self._value

    One change to version 2¶

    Gift cards need the same amount check as accounts. In version 2 it was a method, Account._check_amount, which a gift card cannot reach. It now moves out of the class to a plain module-level function, _check_amount(amount), and every call to self._check_amount(amount) becomes _check_amount(amount). Shared code belongs where everyone who needs it can reach it, and a function does not force a gift card to pretend to be an account.

    Now code that takes payments can accept any Payer:

    def checkout(payer, amount):
    """Charge amount to anything that can pay; return what it returns."""
    return payer.pay(amount)


checkout(linus, 300)      # -300: a checking account, in its overdraft
checkout(card, 120)       # 180: what is left on the gift card
isinstance(card, Payer)   # True
isinstance(card, Account) # False

    Step 3: Duck typing¶

    Look at checkout again. It never checks that payer is a Payer. It just calls pay. That works for any object that has a pay method, whether or not it inherits from Payer:

    class FakePayer:
    """Records payments instead of making them. Useful in tests."""

    def __init__(self):
        self.paid = []

    def pay(self, amount):
        self.paid.append(amount)
        return 0


fake = FakePayer()
checkout(fake, 50)        # 0
fake.paid                 # [50]
isinstance(fake, Payer)   # False, and checkout did not care

    This is duck typing, from the saying "if it walks like a duck and quacks like a duck, it is a duck". Python cares what an object can do, not what it is. An object that cannot do it fails at the moment it is asked:

    checkout("Ada", 50)
# AttributeError: 'str' object has no attribute 'pay'

    ABC or duck typing?¶

    They are two answers to the same question, and Python uses both.

    Formal interface (ABC) Duck typing
    A class opts in by inheriting from the interface having the right methods
    A missing method is caught when the object is created when the method is called
    Works with classes you did not write only if they inherit from it yes
    Best for your own families of classes, frameworks functions that accept "anything that can..."

    The wallet uses both: Payer documents and enforces the contract for its own classes, and checkout stays open to anything that can pay, including test doubles like FakePayer.

    typing.Protocol

    Modern Python can also describe a duck type for tools such as type checkers and editors, with typing.Protocol. A protocol class lists the methods, like an interface, but classes do not need to inherit from it. You will meet it when you start using type hints.

    Step 4: Extend a built-in class¶

    Every transaction should be recorded as a (kind, amount) tuple, such as ("deposit", 200). A plain list would accept anything, including "junk". Built-in types are classes too, so you can subclass list and keep everything it does, while adding your own checks and methods:

    class TransactionLog(list):
    """A list that only accepts (kind, amount) transaction entries."""

    KINDS = ("deposit", "withdraw", "payment", "interest", "fee")

    def __init__(self, entries=()):
        super().__init__()
        self.extend(entries)

    def append(self, entry):
        """Add one entry, after checking it."""
        self._check(entry)
        super().append(entry)

    def extend(self, entries):
        """Add several entries; check them all before adding any."""
        entries = list(entries)
        for entry in entries:
            self._check(entry)
        super().extend(entries)

    def total(self, kind):
        """Return the sum of all amounts of one kind."""
        return sum(amount for k, amount in self if k == kind)

    def _check(self, entry):
        if not isinstance(entry, tuple) or len(entry) != 2:
            raise TypeError("entry must be a (kind, amount) tuple")
        kind, amount = entry
        if kind not in self.KINDS:
            raise ValueError(f"unknown kind: {kind!r}")
        _check_amount(amount)

    Preserve the built-in's behaviour. Each override does its extra work, then calls the real list method through super(). So a TransactionLog still is a list in every way that matters:

    log = TransactionLog()
log.append(("deposit", 200))
log.append(("withdraw", 50))

log                      # [('deposit', 200), ('withdraw', 50)]
len(log)                 # 2
log[0]                   # ('deposit', 200)
for kind, amount in log: # iteration works
    ...
isinstance(log, list)    # True
log.total("deposit")     # 200: the one new method

    And bad entries are refused:

    log.append("junk")                          -> TypeError: entry must be a (kind, amount) tuple
log.append(("gift", 10))                    -> ValueError: unknown kind: 'gift'
log.append(("deposit", -5))                 -> ValueError: amount must be positive
log.extend([("fee", 100), ("deposit", 0)])  -> ValueError: amount must be positive

    After that failed extend, the log is unchanged: neither entry was added, because extend checks everything before adding anything. An operation that fails halfway and leaves half its work done is one of the hardest bugs to track down.

    The trap: list has many doors

    list is written in C, and its methods do not call each other. So overriding append does not guard the other ways in. Even the constructor needed its own override above, because list([...]) never calls append. In this class, these still skip the checks:

    log.insert(0, "junk")     # accepted
log += ["more junk"]      # accepted
log[0] = 42               # accepted

    And slicing or + gives back a plain list, not a TransactionLog. Subclass a built-in when you want all of its behaviour plus a little more, and accept that you guard only the doors you override. When every change must be checked, hold a list inside your class instead of being one: that is the "has a" choice from the last tutorial.

    The wallet is safe with this design because no outside code writes to a history directly. Accounts keep their log in _history, and the public history property hands out a copy.

    Step 5: Multiple inheritance and the MRO¶

    A class can inherit from more than one parent. Python then needs a single, predictable order in which to look for methods. That order is the method resolution order, which you met in the last tutorial, and with several parents it matters more:

    class GiftCard(HistoryMixin, JSONMixin, Payer):
    ...


GiftCard.mro()
# [GiftCard, HistoryMixin, JSONMixin, Payer, ABC, object]

    Python builds this order by three rules: a class comes before its parents, parents keep the left-to-right order you wrote them in, and every class appears exactly once. That last rule matters when two parents share an ancestor, the so-called diamond: every class here eventually inherits from object, yet object appears once, at the end. If the rules cannot all be satisfied, Python refuses to create the class:

    class Broken(ABC, Payer):    # ABC listed before its own subclass
    pass
# TypeError: Cannot create a consistent method resolution order (MRO)
# for bases ABC, Payer

    Multiple inheritance between full, independent class hierarchies gets confusing fast. In practice it is used almost entirely for one job: mixins.

    Step 6: Mixins¶

    A mixin is a small class that adds one piece of behaviour to any class that lists it as a parent. It is not meant to be used on its own, and it is not an "is a" relationship. A gift card is not a history; it has the history behaviour mixed in.

    The wallet needs two pieces of behaviour that both accounts and gift cards share, and that have nothing to do with money rules: keeping a history, and turning into JSON.

    class HistoryMixin:
    """Give a class a transaction history."""

    def _record(self, kind, amount):
        """Add one entry to this object's history."""
        if "_history" not in vars(self):
            self._history = TransactionLog()
        self._history.append((kind, amount))

    @property
    def history(self):
        """A copy of the transaction history."""
        return TransactionLog(vars(self).get("_history", ()))


class JSONMixin:
    """Give a class a dictionary and JSON form of its simple attributes."""

    def to_dict(self):
        """Return the type and simple attributes as a dictionary."""
        data = {"type": type(self).__name__}
        for name, value in vars(self).items():
            if isinstance(value, (str, int, float, bool)):
                data[name.lstrip("_")] = value
        return data

    def to_json(self):
        """Return to_dict() as a JSON string."""
        return json.dumps(self.to_dict())

    Mix them in by listing them first, before the main base class:

    class Account(HistoryMixin, JSONMixin, Payer):
    ...


class GiftCard(HistoryMixin, JSONMixin, Payer):
    ...

    Then each method that moves money records it with one line, for example self._record("deposit", amount) in deposit, self._record("payment", amount) in GiftCard.pay, and self._record("fee", self.fee) when a checking account is charged. Notice the overrides from the last tutorial: CheckingAccount.withdraw replaces the parent's method entirely, so it must record the withdrawal itself. Keeping the parent's promises includes this one.

    Both families now get both behaviours, written once:

    linus.history       # [('withdraw', 300), ('fee', 100)]
grace.to_dict()     # {'type': 'SavingsAccount', 'owner': 'Grace', 'balance': 1020, 'rate': 2}
card.to_json()      # '{"type": "GiftCard", "code": "HB-2026", "value": 180}'

    to_dict keeps only simple values, so the history log is left out, and strips the leading underscore, so _owner becomes owner.

    Good mixins follow a few rules:

    • One job each. A mixin's name says what it adds: HistoryMixin, JSONMixin.
    • No __init__ of its own, if possible. HistoryMixin creates its log the first time it is needed, so it does not have to take part in the classes' constructors.
    • Mixins first, main base last, as in class GiftCard(HistoryMixin, JSONMixin, Payer). Python searches left to right, so the mixins' methods are found first and the main base class sits at the end.
    • Ask whether it is really shared. If only one class needs the behaviour, put it in that class.

    The code so far¶

    This is version 3 of the wallet, tagged v3-abstract in the companion repository. It has grown, so read it top to bottom once: the helpers and mixins first, then the interface, the abstract Account with its two subclasses, the gift card, and checkout.

    wallet.py · version 3
    wallet.py
    #!/usr/bin/env python3
"""A small digital wallet, built up across the OOP tutorials.

Version 3: Abstract Classes & Interfaces.
"""
import json
from abc import ABC, abstractmethod


def _check_amount(amount):
    """Raise if amount is not a positive whole number."""
    if isinstance(amount, bool) or not isinstance(amount, int):
        raise TypeError("amount must be an integer")
    if amount <= 0:
        raise ValueError("amount must be positive")


class TransactionLog(list):
    """A list that only accepts (kind, amount) transaction entries."""

    KINDS = ("deposit", "withdraw", "payment", "interest", "fee")

    def __init__(self, entries=()):
        super().__init__()
        self.extend(entries)

    def append(self, entry):
        """Add one entry, after checking it."""
        self._check(entry)
        super().append(entry)

    def extend(self, entries):
        """Add several entries; check them all before adding any."""
        entries = list(entries)
        for entry in entries:
            self._check(entry)
        super().extend(entries)

    def total(self, kind):
        """Return the sum of all amounts of one kind."""
        return sum(amount for k, amount in self if k == kind)

    def _check(self, entry):
        if not isinstance(entry, tuple) or len(entry) != 2:
            raise TypeError("entry must be a (kind, amount) tuple")
        kind, amount = entry
        if kind not in self.KINDS:
            raise ValueError(f"unknown kind: {kind!r}")
        _check_amount(amount)


class HistoryMixin:
    """Give a class a transaction history."""

    def _record(self, kind, amount):
        """Add one entry to this object's history."""
        if "_history" not in vars(self):
            self._history = TransactionLog()
        self._history.append((kind, amount))

    @property
    def history(self):
        """A copy of the transaction history."""
        return TransactionLog(vars(self).get("_history", ()))


class JSONMixin:
    """Give a class a dictionary and JSON form of its simple attributes."""

    def to_dict(self):
        """Return the type and simple attributes as a dictionary."""
        data = {"type": type(self).__name__}
        for name, value in vars(self).items():
            if isinstance(value, (str, int, float, bool)):
                data[name.lstrip("_")] = value
        return data

    def to_json(self):
        """Return to_dict() as a JSON string."""
        return json.dumps(self.to_dict())


class Payer(ABC):
    """Interface: anything that can pay an amount."""

    @abstractmethod
    def pay(self, amount):
        """Pay amount, or raise ValueError; return what is left."""


class Account(HistoryMixin, JSONMixin, Payer):
    """Abstract base for wallet accounts holding money, in whole lek."""

    currency = "ALL"

    def __init__(self, owner, balance=0):
        """Create an account for owner with an opening balance."""
        self.owner = owner
        if isinstance(balance, bool) or not isinstance(balance, int):
            raise TypeError("balance must be an integer")
        if balance < 0:
            raise ValueError("balance must not be negative")
        self._balance = balance
        if balance:
            self._record("deposit", balance)

    @property
    def owner(self):
        """The account holder's name."""
        return self._owner

    @owner.setter
    def owner(self, value):
        if not isinstance(value, str):
            raise TypeError("owner must be a string")
        if not value.strip():
            raise ValueError("owner must not be empty")
        self._owner = value.strip()

    @property
    def balance(self):
        """The current balance. Read-only: use deposit and withdraw."""
        return self._balance

    def deposit(self, amount):
        """Add amount to the balance and return the new balance."""
        _check_amount(amount)
        self._balance += amount
        self._record("deposit", amount)
        return self._balance

    def withdraw(self, amount):
        """Take amount from the balance and return the new balance."""
        _check_amount(amount)
        if amount > self._balance:
            raise ValueError("insufficient funds")
        self._balance -= amount
        self._record("withdraw", amount)
        return self._balance

    def pay(self, amount):
        """Pay amount from this account; return the new balance."""
        return self.withdraw(amount)

    @abstractmethod
    def month_end(self):
        """Apply end-of-month rules and return the new balance."""

    def __str__(self):
        return f"{self.owner}: {self.balance} {self.currency}"

    def __repr__(self):
        return (f"{type(self).__name__}(owner={self.owner!r}, "
                f"balance={self.balance})")


class SavingsAccount(Account):
    """An account that earns interest every month."""

    def __init__(self, owner, balance=0, rate=1):
        """Create a savings account; rate is monthly interest in percent."""
        super().__init__(owner, balance)
        if isinstance(rate, bool) or not isinstance(rate, int):
            raise TypeError("rate must be an integer")
        if not 0 <= rate <= 10:
            raise ValueError("rate must be between 0 and 10")
        self._rate = rate

    @property
    def rate(self):
        """Monthly interest rate, in whole percent."""
        return self._rate

    def add_interest(self):
        """Add this month's interest and return the amount added."""
        interest = self._balance * self._rate // 100
        if interest > 0:
            self._balance += interest
            self._record("interest", interest)
        return interest

    def month_end(self):
        """Add this month's interest and return the new balance."""
        self.add_interest()
        return self._balance

    def __repr__(self):
        return (f"{type(self).__name__}(owner={self.owner!r}, "
                f"balance={self.balance}, rate={self.rate})")


class CheckingAccount(Account):
    """An everyday account that may go below zero, up to a limit."""

    fee = 100

    def __init__(self, owner, balance=0, overdraft=0):
        """Create a checking account with an overdraft limit."""
        super().__init__(owner, balance)
        if isinstance(overdraft, bool) or not isinstance(overdraft, int):
            raise TypeError("overdraft must be an integer")
        if overdraft < 0:
            raise ValueError("overdraft must not be negative")
        self._overdraft = overdraft

    @property
    def overdraft(self):
        """How far below zero the balance may go."""
        return self._overdraft

    def withdraw(self, amount):
        """Take amount out, letting the balance go down to -overdraft."""
        _check_amount(amount)
        if self._balance - amount < -self._overdraft:
            raise ValueError("overdraft limit exceeded")
        self._balance -= amount
        self._record("withdraw", amount)
        return self._balance

    def month_end(self):
        """Charge the monthly fee if overdrawn; return the new balance."""
        if self._balance < 0:
            self._balance -= self.fee
            self._record("fee", self.fee)
        return self._balance

    def __str__(self):
        return f"{super().__str__()} (overdraft {self.overdraft})"

    def __repr__(self):
        return (f"{type(self).__name__}(owner={self.owner!r}, "
                f"balance={self.balance}, overdraft={self.overdraft})")


class GiftCard(HistoryMixin, JSONMixin, Payer):
    """A prepaid card with a fixed value. It is not an account."""

    currency = "ALL"

    def __init__(self, code, value):
        """Create a gift card with a code and a starting value."""
        if not isinstance(code, str) or not code.strip():
            raise ValueError("code must be a non-empty string")
        _check_amount(value)
        self._code = code.strip()
        self._value = value

    @property
    def value(self):
        """What is left on the card."""
        return self._value

    def pay(self, amount):
        """Pay amount from the card; return the value left."""
        _check_amount(amount)
        if amount > self._value:
            raise ValueError("not enough value on the card")
        self._value -= amount
        self._record("payment", amount)
        return self._value

    def __str__(self):
        return f"Gift card {self._code}: {self.value} {self.currency}"

    def __repr__(self):
        return f"GiftCard(code={self._code!r}, value={self.value})"


def checkout(payer, amount):
    """Charge amount to anything that can pay; return what it returns."""
    return payer.pay(amount)


if __name__ == "__main__":
    grace = SavingsAccount("Grace", 1000, rate=2)
    linus = CheckingAccount("Linus", overdraft=500)
    card = GiftCard("HB-2026", 300)

    checkout(linus, 300)
    checkout(card, 120)
    for account in (grace, linus):
        account.month_end()

    for item in (grace, linus, card):
        print(item)
    print(linus.history)
    print(card.to_json())

    ./wallet.py

Linus: -400 ALL (overdraft 500)
Gift card HB-2026: 180 ALL

    When something goes wrong¶

    TypeError: Can't instantiate abstract class ... without an implementation for abstract method ...

    You created an abstract class, or a subclass that does not define every abstract method. Add the method named in the message, with exactly that name. A typo such as month_End leaves the real one still missing.

    My abstract class can be created, and it should not

    The method is missing its @abstractmethod decorator, or the class does not inherit from ABC, directly or through a parent such as Payer.

    AttributeError: '...' object has no attribute 'pay'

    Duck typing at work: the object passed in cannot do what the function asks. Either pass an object that has the method, or check the caller.

    TypeError: Cannot create a consistent method resolution order (MRO)

    The parent classes are listed in an order Python cannot satisfy, usually a class placed before one of its own subclasses. Put mixins first and the main base class last.

    My list subclass accepted something it should have refused

    It came in through a door you did not override, such as insert, +=, item assignment or the constructor. Override that method too, or hold a list inside the class instead of subclassing it.
