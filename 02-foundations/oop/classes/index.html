    Classes & Object Model¶

    75 min Object-Oriented Design Needs: Exception Handling

    Until now your data and the functions that work on it have lived apart: a balance in one variable, a deposit function somewhere else. A class puts them together. In this tutorial you build the first piece of a small digital wallet, an Account that holds money, refuses bad input and protects its own balance. The rest of the module keeps building on it.

    Why this matters¶

    Programs model things: users, orders, accounts, bookings. Each thing has data (an account has an owner and a balance) and rules (the balance can never go below zero). Without classes, nothing stops some other part of the program from breaking those rules. With a class, the data and the rules travel together, and the object itself refuses to get into an invalid state.

    Almost every framework you will use later, from web back-ends to the HBnB portfolio project, is built from classes. Reading and designing them is a core skill.

    The running example¶

    One wallet grows across all five projects of this module. This page builds version 1.

    Every finished version is saved in the companion repository, evisp/oop-wallet, under a tag. Write the code yourself as you read, then compare it with the tag.

    Step 1: Design before you type¶

    Start from a description of what the program must do, in plain words:

    A customer has an account with a balance, in lek. They can deposit and withdraw money. The balance can never go below zero, and nobody may change it directly.

    Read it and sort the words. Nouns that have their own data become classes and attributes. Verbs become methods. Rules become validation.

    In the description Becomes In code
    account a class Account
    customer, balance attributes owner, balance
    deposit, withdraw methods deposit(), withdraw()
    never below zero a check that raises ValueError("insufficient funds")
    nobody changes it directly protected state a read-only balance

    Five minutes on this table saves an hour of rewriting. You will draw the same design formally in the UML project.

    Step 2: Class and instance¶

    A class is a blueprint: it describes what every account has and can do. An instance, or object, is one account built from that blueprint, with its own data.

    The smallest possible class has no body at all:

    class Account:
    pass


ada = Account()
linus = Account()
print(type(ada))      # <class '__main__.Account'>
print(ada is linus)   # False: two separate objects

    Calling the class, Account(), builds a new instance. ada and linus come from the same blueprint, but they are two separate objects. That is the whole idea: one class, as many instances as you need, each with its own state.

    Class names use CapitalisedWords. Function, method and variable names stay in lower_case, as before.

    Step 3: __init__ and self¶

    An empty account is not much use. Every account should start with an owner and a balance. The special method __init__ runs automatically each time an instance is created, and it sets up that instance's attributes:

    class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance


ada = Account("Ada", 500)
linus = Account("Linus")
print(ada.owner, ada.balance)      # Ada 500
print(linus.owner, linus.balance)  # Linus 0

    self is the instance being built. When you write Account("Ada", 500), Python creates an empty object, then calls __init__ with that object as self, "Ada" as owner and 500 as balance. self.owner = owner stores the name on that object, which is why ada and linus each keep their own.

    You can see an instance's own attributes with vars:

    vars(ada)    # {'owner': 'Ada', 'balance': 500}

    __init__ is called the initialiser. It never returns a value; its only job is to put the new object into a sensible starting state.

    Step 4: Methods that work on the object's state¶

    A method is a function defined inside a class. Its first parameter is always self, so it can read and change the instance it was called on.

    class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance

    def deposit(self, amount):
        self.balance += amount
        return self.balance

    def withdraw(self, amount):
        self.balance -= amount
        return self.balance


ada = Account("Ada", 500)
ada.deposit(200)     # 700
ada.withdraw(100)    # 600

    ada.deposit(200) is shorthand. Python turns it into Account.deposit(ada, 200): it looks up deposit on the class and passes ada in as self. Try both; they do exactly the same thing. That is the entire mystery of self: it is the object before the dot.

    Notice that the methods return the new balance, as you learned in Functions & Modularity. They do not print. Whoever uses the class decides what to show.

    Step 5: Validate input when constructing objects¶

    The class works, and it is already broken. Try these:

    ada.withdraw(10_000)        # -9350: the balance is now negative
ada.deposit(-500)           # a "deposit" that removes money
bad = Account("", "lots")   # an account with no owner and a text balance
ada.balance = 1_000_000     # anyone can set any balance

    Every line breaks a rule from the description in Step 1, and Python accepts all of them. The class must enforce its own rules. The approach is the one from Exception Handling: check the input and raise a specific exception.

    class Account:
    def __init__(self, owner, balance=0):
        if not isinstance(owner, str):
            raise TypeError("owner must be a string")
        if not owner.strip():
            raise ValueError("owner must not be empty")
        if isinstance(balance, bool) or not isinstance(balance, int):
            raise TypeError("balance must be an integer")
        if balance < 0:
            raise ValueError("balance must not be negative")
        self.owner = owner.strip()
        self.balance = balance

    def deposit(self, amount):
        self._check_amount(amount)
        self.balance += amount
        return self.balance

    def withdraw(self, amount):
        self._check_amount(amount)
        if amount > self.balance:
            raise ValueError("insufficient funds")
        self.balance -= amount
        return self.balance

    def _check_amount(self, amount):
        if isinstance(amount, bool) or not isinstance(amount, int):
            raise TypeError("amount must be an integer")
        if amount <= 0:
            raise ValueError("amount must be positive")

    Now the broken calls fail loudly and clearly:

    Account("", 100)         -> ValueError: owner must not be empty
Account(42)              -> TypeError: owner must be a string
Account("Ada", -5)       -> ValueError: balance must not be negative
Account("Ada", "lots")   -> TypeError: balance must be an integer
ada.withdraw(10_000)     -> ValueError: insufficient funds
ada.deposit(-500)        -> ValueError: amount must be positive
ada.deposit(2.5)         -> TypeError: amount must be an integer

    Three design points are worth noticing:

    • Validate in __init__. If the constructor checks everything, an invalid Account can never exist. Every other method can then trust the object's state.
    • One helper, used twice. deposit and withdraw both need the same amount check, so it lives in one method, _check_amount. The leading underscore says it is for the class's own use, not for callers. More on that in the next step.
    • Why the bool check? In Python, True passes isinstance(True, int), and True + 1 is 2. Without the extra check, ada.deposit(True) would quietly add 1 lek. The reason is that bool is a subclass of int, which is exactly what the next tutorial is about.

    Amounts are whole numbers of lek on purpose. Floating-point numbers cannot store most decimal fractions exactly, so 0.1 + 0.2 is not 0.3. Real financial software stores money as whole units for the same reason.

    Step 6: Control access to internal attributes¶

    One line from Step 5 still works: ada.balance = 1_000_000. The validation in deposit and withdraw means nothing if anyone can write to balance directly. This is what encapsulation is about: the object keeps its data behind a small set of methods, and those methods are the only way in.

    Python has no truly private attributes. Instead it uses naming conventions, and one tool, the property, that lets you control exactly how an attribute is read and written.

    _name: "internal, please do not touch"¶

    A single leading underscore marks an attribute or method as internal. Python does not stop anyone from using it, but every Python developer reads it as "not part of the public interface; may change without warning". You already used it for _check_amount.

    __name: name mangling¶

    Two leading underscores make Python rename the attribute behind the scenes, which is called name mangling:

    class Card:
    def __init__(self, pin):
        self.__pin = pin


card = Card(1234)
card.__pin           # AttributeError: 'Card' object has no attribute '__pin'
vars(card)           # {'_Card__pin': 1234}
card._Card__pin      # 1234

    __pin was stored as _Card__pin. That protects it from accidental clashes, especially in subclasses, but it is not security: anyone who knows the rule can still reach it. In this wallet we use a single underscore, because the account types you build in the next tutorial will need to work with the balance too.

    @property: control reading and writing¶

    A property looks like an attribute from outside, but runs a method when it is read or written. Store the real value in _balance, and expose a balance property with only a getter:

        @property
    def balance(self):
        """The current balance. Read-only: use deposit and withdraw."""
        return self._balance

    Reading works exactly as before, and writing is now refused:

    ada.balance               # 700
ada.balance = 1_000_000   # AttributeError: property 'balance' of 'Account' object has no setter

    For owner, renaming should be allowed but still validated. A property can have a setter as well, which runs on every assignment:

        @property
    def owner(self):
        """The account holder's name."""
        return self._owner

    @owner.setter
    def owner(self, value):
        if not isinstance(value, str):
            raise TypeError("owner must be a string")
        if not value.strip():
            raise ValueError("owner must not be empty")
        self._owner = value.strip()

    ada.owner = "  Ada Lovelace "   # stored as 'Ada Lovelace'
ada.owner = ""                  # ValueError: owner must not be empty

    Here is the neat part: inside __init__, write self.owner = owner. That assignment goes through the setter too, so the owner checks live in one place and run both when the account is created and whenever it is renamed later.

    Step 7: String representations¶

    Print an object with no string methods and you get its type and memory address, which tells you nothing:

    print(ada)    # <__main__.Account object at 0x7f3ed9336cf0>

    Two special methods fix this, each for a different reader:

    • __str__ is for people. print() and str() use it.
    • __repr__ is for developers. The interpreter, debuggers, and lists of objects use it. A good __repr__ looks like the code that would rebuild the object.
        def __str__(self):
        return f"{self.owner}: {self.balance} {self.currency}"

    def __repr__(self):
        return f"Account(owner={self.owner!r}, balance={self.balance})"

    print(ada)          # Ada: 600 ALL
repr(ada)           # "Account(owner='Ada', balance=600)"
print([ada, linus]) # [Account(owner='Ada', balance=600), Account(owner='Linus', balance=0)]
f"{ada} | {ada!r}"  # 'Ada: 600 ALL | Account(owner='Ada', balance=600)'

    Notice the list: printing a list shows its items with __repr__, not __str__. If you only write one of the two, write __repr__; Python falls back to it when there is no __str__.

    Both methods return a string. Neither prints.

    Step 8: Class attributes¶

    Some data belongs to the class, not to any one account. Every account in this wallet uses the same currency, so it is defined once, directly in the class body:

    class Account:
    """A wallet account holding money, in whole lek."""

    currency = "ALL"

    Account.currency            # 'ALL'
ada.currency                # 'ALL': found on the class
"currency" in vars(ada)     # False: ada does not store its own copy

    When you read ada.currency, Python looks on the instance first, and then on the class. Change the class attribute and every instance sees the change. But assigning ada.currency = "USD" does not change the class: it creates a new attribute on ada alone, which then hides the class one. Use class attributes for values that really are shared, such as constants, and change them only through the class.

    The code so far¶

    This is version 1 of the wallet. It is also tagged v1-classes in the companion repository.

    wallet.py · version 1
    wallet.py
    #!/usr/bin/env python3
"""A small digital wallet, built up across the OOP tutorials.

Version 1: Classes & Object Model.
"""


class Account:
    """A wallet account holding money, in whole lek."""

    currency = "ALL"

    def __init__(self, owner, balance=0):
        """Create an account for owner with an opening balance."""
        self.owner = owner
        if isinstance(balance, bool) or not isinstance(balance, int):
            raise TypeError("balance must be an integer")
        if balance < 0:
            raise ValueError("balance must not be negative")
        self._balance = balance

    @property
    def owner(self):
        """The account holder's name."""
        return self._owner

    @owner.setter
    def owner(self, value):
        if not isinstance(value, str):
            raise TypeError("owner must be a string")
        if not value.strip():
            raise ValueError("owner must not be empty")
        self._owner = value.strip()

    @property
    def balance(self):
        """The current balance. Read-only: use deposit and withdraw."""
        return self._balance

    def deposit(self, amount):
        """Add amount to the balance and return the new balance."""
        self._check_amount(amount)
        self._balance += amount
        return self._balance

    def withdraw(self, amount):
        """Take amount from the balance and return the new balance."""
        self._check_amount(amount)
        if amount > self._balance:
            raise ValueError("insufficient funds")
        self._balance -= amount
        return self._balance

    def _check_amount(self, amount):
        """Raise if amount is not a positive whole number."""
        if isinstance(amount, bool) or not isinstance(amount, int):
            raise TypeError("amount must be an integer")
        if amount <= 0:
            raise ValueError("amount must be positive")

    def __str__(self):
        return f"{self.owner}: {self.balance} {self.currency}"

    def __repr__(self):
        return f"Account(owner={self.owner!r}, balance={self.balance})"


if __name__ == "__main__":
    ada = Account("Ada", 500)
    ada.deposit(200)
    ada.withdraw(100)
    print(ada)
    print(repr(ada))

    ./wallet.py

    Ada: 600 ALL
Account(owner='Ada', balance=600)

    The file passes pycodestyle, and the demo runs only under if __name__ == "__main__":, so other files can import Account without printing anything.

    AI in the loop

    Paste your class into an assistant and ask it to attack it: "Find inputs or sequences of calls that put this Account into an invalid state. Don't fix anything, just list them." Then decide for each one whether your class should prevent it, and fix it yourself. Thinking like someone trying to break your object is the fastest way to learn what encapsulation is for.

    When something goes wrong¶

    TypeError: Account.__init__() takes from 2 to 3 positional arguments but 4 were given

    Python counts self as one of the arguments. Check the number of values you pass matches the parameters after self.

    TypeError: Account.deposit() missing 1 required positional argument: 'amount'

    Usually you called the method on the class, Account.deposit(200), instead of on an instance, ada.deposit(200). Or you forgot self as the first parameter of the method.

    NameError: name '_balance' is not defined inside a method

    Attributes always need self. in front: self._balance, not _balance.

    RecursionError: maximum recursion depth exceeded in a property

    The property stores its value under its own name, for example self.owner = value inside the owner setter, so the setter calls itself forever. Store it under the underscore name: self._owner.

    AttributeError: property 'balance' of 'Account' object has no setter

    That is the class working as designed. Change the balance through deposit and withdraw.

    Quick reference¶

    Code What it does
    class Account: Define a class
    Account("Ada", 500) Create an instance; runs __init__
    def __init__(self, ...): Set up a new instance's attributes
    self.x = value Store an attribute on the instance
    def method(self, ...): Define a method; self is the object before the dot
    _name / __name Internal by convention / name-mangled
    @property Read an attribute through a method
    @x.setter Validate or refuse writes to x
    __str__ / __repr__ Text for people / text for developers
    vars(obj) Show an instance's own attributes
